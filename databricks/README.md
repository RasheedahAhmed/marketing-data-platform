Run `scripts/render_grants.py` with your real principal and catalog, then have a metastore/catalog administrator review and execute the generated SQL. The final SELECT grants require a successful build first; run those statements afterward. This avoids granting readers access to raw facts or deleted records.

Create the `marketing_analysts` group before executing group grants. The runtime principal receives no CREATE CATALOG or metastore-wide privileges. Admin creates all known schemas; dbt uses its default `<target_schema>_<custom_schema>` naming. SQL `CREATE TABLE` on a schema also permits view creation in Unity Catalog; do not copy invalid catalog-scoped grants from the assignment example.

Upload all nine original CSVs, with filenames unchanged, into the `landing.marketing_files` Volume. The upload operator needs WRITE VOLUME; the ingestion principal only needs READ VOLUME. Launch `01_ingest_csv.py` as a notebook task on Unity Catalog-enabled Python compute. Fill its catalog, bronze_schema and input_path widgets. Raw data is all strings, retains duplicate rows, and includes SHA-256 row and batch metadata. Complete batches are retained; apply a separate retention policy only after confirming that no builds need them.

Run ingestion and `python scripts/run_dbt.py --target <target>` sequentially. Configure max_concurrent_runs=1 for the entire environment pipeline. In CI, use an isolated catalog containing pre-ingested test data. Do not run multiple writers against one target schema. The runner freezes the published raw batch ID, so a later pointer change cannot mix source snapshots during a build.

Workspace administrator steps: assign the service principal to the workspace, grant SQL Warehouse CAN USE, grant permission to run/use the ingestion compute, set the production job Run as to the service principal, and create its Databricks OAuth secret. Supply that secret to the runtime secret manager or GitHub environment secret, never notebook source. This is a Databricks OAuth credential; an Azure application secret is not automatically interchangeable.

The dbt fact MERGE is atomic for one table. The complete collection of dbt model replacements is not a cross-table transaction. Downstream reporting should refresh only after the pipeline has succeeded; dbt build failure must not trigger a BI refresh. At larger scale, publish versioned marts with a release pointer.
